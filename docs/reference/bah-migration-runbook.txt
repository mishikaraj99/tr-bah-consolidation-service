Build-A-Habit is two systems sharing one write path: the legacy 3/7/21 streak flow, which
carries effectively 100% of production traffic, and the v85 Habit Tracker revamp, which is
deployed but has almost no installed base. This document is the ground truth, the measured
traffic, the difference between the two systems, the full endpoint inventory, and a ticket-by-ticket
order to work through.

The seam
Both economies are selected inside one api-server endpoint. POST /activityLogForBAH reads
isHabitTracker straight from the request body; shouldUseHabitTrackerCredit() then either calls
app-backend's scratch-card mint (v85) or runs the local 3/7/21 credit (legacy). GET
/bahLogForGivenDate branches on appVersion >= 85, and both app versions call it for the dose
list.
So api-server owns the write path and the dose list for v85 users too. The revamp moved the
display surface to app-backend and left the writes behind. Finishing the migration is about
moving that write path, not about rebuilding v85.

Correction to the earlier draft
An earlier version of this document said v85 was "already live and already served by
app-backend" and listed /bah/:userId/calendar, /bahDetailDateWiseLikePagination,
/activityLogsBAH and /coinRewardHistory as endpoints superseded by v85 and therefore
sunset candidates. The traffic data contradicts that. v85 is deployed but not rolled out, so
nothing is being superseded: /bah/:userId/calendar (402,045 a week) and /coinTransaction
(476,051 a week) are the third and fourth busiest BAH endpoints and must be migrated, not
retired.

06 — The plan: 22 tickets, picked up one
at a time
Every ticket is independently shippable and independently revertible. Rules that apply to all of
them: app-backend deploys to master first; one ticket per deploy; a write never shares a deploy
with a read; and every route change lands in both deployments.
The ordering principle is shrink, then secure, then migrate in ascending blast radius. Waves
0 and 1 remove 17 endpoints and fix two live defects before any traffic moves, which cuts the
surface from 38 endpoints to 21 and makes every later ticket smaller.

09 — Per-cutover checklist
Run this for every ticket in Waves 2 and 3, not once for the migration.
  1.​ Diff both cohorts — legacy and v85 — api-server local vs app-backend, field by field
      including nulls and array ordering.
  2.​ Deploy app-backend to master first. The proxy target must exist in production before
    the proxy does.
3.​ Confirm the env vars that ticket needs are present in the environment you just deployed
    to.
4.​ Flip the route and ship. One ticket per deploy; a write never shares a deploy with a read.
5.​ Watch a full day in Last9 — request count, error rate and p95 on that route, in BOTH
    traya-api-server-prod-prod and traya-internal-api-service-prod-prod. For writes, also the
    count of reward transactions per log, split by cohort.
6.​ Only then delete the local handler, and only once nothing in section 05 imports it.
